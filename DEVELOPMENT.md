# DSH Plugin Development Version

Current worktree: `0.3.0-dev.1` (unreleased), with bounded repair rounds, pause/resume, and candidate verification queue recovery added; the released baseline is `v0.2.0-dev.1`. It is still not the complete first version.

Already implemented: an independent Runtime, SQLite state/events/command dedup/outbox, host tools, worker checkpoint/submit, one DSH SDK process per Attempt, working copies, cancellation and timeout, SSE event replay, conservative restart recovery, content-digest-bound Candidate snapshots, fresh read-only review Attempts, independent acceptance commands, and a deterministic Gate.

Explicitly enabled integration, final acceptance, conditional keep-current-files handling, and conflict-resolution work items have been added. Not yet implemented: full RunSpec, strong-evidence reconciliation of unknown processes, slash commands, and OpenCode/Pi adapters. Artifacts already support paginated reads and change manifests, but there is no bulk archive export yet. Unimplemented capabilities are never displayed as successful. For the remaining full-development direction see [ROADMAP.md](./ROADMAP.md).

## Development and verification

Requires Node.js >= 22.13; the local verification environment is Windows, Node.js 22.22.1, DSH/SDK/tools `0.1.2-rc.1`, Cordis `4.0.2`. Node 22's built-in SQLite shows an experimental warning.

```powershell
Set-Location C:\work\teamwork-dsh
npm ci --registry=https://registry.npmjs.org

```

There are currently 243 automated tests. The real DSH tests cover a single implementer, full review/Gate, per-requirement review of structured requirements, a four-process requirement-revision and failure-repair chain, and a three-process recovery chain of "checkpoint → interrupt and confirm exit → new implementer → new review → acceptance"; the offline LLM adapter calls the real tools, sends no network model requests, and requires no API key. The explicit integration test further writes a real DSH candidate back to a temporary project, preserving user files added in the meantime and re-accepting; the conflict chain covers reading three-way content, producing a new candidate, independent review, and explicit integration again. Other tests cover dedup, identity/version rejection, candidate and context tampering, read-credential revocation, failure/timeout/input rewriting, pause races, reload, artifact permissions and pagination, three-way conflicts, SQLite recovery, real child-process exit boundaries, cancellation, keep-current-files, requirement revision and descendant invalidation, historical baselines, new work-item transaction rollback, out-of-scope changes, and missing/duplicate requirement IDs. Whole-task-chain control tests cover aggregate revisions, parent/child holds, shared-budget exhaustion, cancellation isolation, transaction rollback, final write-back interruption/drain, and persistent recovery; 16 new lifecycle tests cover attached/persistent real DSH processes, exit, and pause evidence. This is not equivalent to real-model effectiveness or multi-day continuous-operation acceptance.

Tests use only a temporary DSH_HOME and do not modify the user's DSH profile. Temporary copies and state generated by tests are cleaned up afterward.

## Starting the Runtime

Edit `examples/runtime.example.json`: `workspace` is the project authorized to the worker; `dataDirectory` must be outside that project and in a directory private to the current user; configure the model routing to the DSH provider/model you already have. The example does not write or replace credentials.

```powershell
# Only checks the version and SDK initialization; does not submit a task.
npm start -- --config C:\work\teamwork-dsh\examples\runtime.example.json --doctor

# Default attached: pauses work when the owner exits, releases the database owner after exit is confirmed.
npm start -- --config C:\work\teamwork-dsh\examples\runtime.example.json

# Explicit persistent: runs independently after the start command returns; terminal/DSH entry exit does not stop authorized work.
npm start -- start --config C:\work\teamwork-dsh\examples\runtime.example.json

# Query the standalone service (including instanceId); does not read or print model credentials.
npm start -- status --config C:\work\teamwork-dsh\examples\runtime.example.json

# Stop the entire Runtime, not cancel a single task. Use the real instanceId from the previous step.
npm start -- stop --config C:\work\teamwork-dsh\examples\runtime.example.json --instance-id <instanceId> --command-id stop-runtime-001 --mode drain
```

The Runtime outputs the instance ID and the `connection.json` path, and does not output tokens. An empty data directory runs the model only after the first `teamwork_start`; on restart it still recovers authorized, unpaused pending-dispatch work. DSH uses existing credentials according to the selected profile. Starting DSH itself may initialize a missing profile per its normal behavior; this plugin does not change the global model selection, nor does it register a system service or startup entry.

One data directory serves one workspace, a fixed execution profile, acceptance policy, integration enablement state, and CLI lifecycle. When changing workspace/model/profile/verification, enabling integration, switching attached/persistent, or upgrading from an old CLI data directory not bound to a lifecycle, use a new data directory; old authorizations are not migrated automatically. Do not delete old state/backups because of this. Do not modify profile/overlay files and external acceptance scripts while running; the current digest records the configured values and does not freeze the contents of these external files.

### Attached vs. persistent run boundaries

By default the `run` CLI process is the attached owner; the Runtime is in an independent child process and detects owner exit over IPC, including when the owner is killed directly. After disconnect it records a global pause and requests interruption of current execution, fixing the checkpoint/candidate once exit is confirmed. Here the owner is the CLI that started `run`, not any DSH session connected to it. `start` launches a persistent child process; disconnecting the launcher or any DSH entry does not trigger a pause; existing authorized scope and shared budget still apply. Run saves the lifecycle and derived tasks inherit it.

The launcher uses a hidden window, a detached process, and independent stdio, and waits for an IPC ready receipt; it does not declare startup success merely because a PID exists. See the [Node.js child_process documentation](https://nodejs.org/docs/latest-v22.x/api/child_process.html#optionsdetached). A startup-observation timeout returns STARTUP_UNCONFIRMED, which does not prove the child has stopped, and it does not automatically kill the process or start another copy; check with `status` first. Repeated starts are rejected when an owner already exists. Machine shutdown, sleep, and the process's own crash are not covered by the "continue after entry disconnect" guarantee, and there is currently no automatic restart after a crash or unknown-process reconciliation.

`runtime-service.json` is for operator management only and contains a standalone operator token; the host plugin only reads `connection.json`, never obtains management credentials, and worker credentials cannot access the management API. Both must be placed in a data directory private to the current user. The management API is GET `/v1/runtime` and POST `/v1/runtime/commands`; it does not accept a browser Origin; a stop request requires `{type:"stop",instanceId,commandId,mode}`. The instance ID prevents an old terminal from accidentally stopping a replacement service; the CLI does not signal the PID recorded.

The default drain for stop first, in one SQLite transaction, saves all root/descendant pauses, blocks subsequent dispatch and automatic write-back, and records a unique operator receipt; then it waits for the current execution/final write-back to drain normally. interrupt requests immediate stop of owned execution and may leave partial writes and integrations pending reconciliation. An existing drain can be upgraded to interrupt with a new commandId; an already requested interrupt cannot be downgraded by repeating the old command. CLI Ctrl+C / attached-owner disconnect uses interrupt.

`accepted: true` is a receipt of the stop request, not that it has stopped; only querying `stopped` means execution exit is confirmed, HTTP/database are closed, and the owner has been released. During shutdown the port/record handover may briefly return SERVICE_UNREACHABLE or SERVICE_TRANSITION; keep querying the same instance and do not start a replacement process based on that. An unknown worker or final-command exit retains the owner, the management entry, and blocked state. A stopped but partially integrated run that still needs reconciliation retains files, backups, and the source lease; closing the service does not mean it passed acceptance.

After a clean stop, restarting the same mode can re-query persistent tasks but will not automatically resume a manually paused task tree; when needed, use `scope: workflow` resume, which preserves consumed budget and new Attempt identity. After the service stops, a stop retry reports SERVICE_STOPPED; a still-running service replays the original receipt for the same commandId/content. `status` reports unknown when the service is offline but there is no explicit stopped record; it does not infer safe stop from a missing PID.

State records use atomic replacement of a temporary file in the same directory, do not follow links, and do not truncate in place; a brief replacement refusal caused by concurrent Windows reads is retried a limited number of times only for the same metadata publication, without replaying model work or file integration. Lifecycle tests include real DSH, launcher exit, forced owner exit, observation timeout, stale instances, transaction failure, and SQLite reopen; these short tests still do not prove multi-day continuous autonomous operation.

## Enabling independent review and acceptance

Without a `verification` configuration, the old report-collection mode is retained. Once configured, each start additionally launches a review DSH process (same model routing, but a fresh session), which may increase model cost. The acceptance configuration can only be specified by the operator in the Runtime JSON; model tools have no permission to modify it.

See the full example in `examples/runtime.verification.example.json`: the project `examples/verification-project/sum.mjs` deliberately does not handle empty arrays, so you can submit the task "fix sum's behavior for empty arrays to return 0 while keeping other summation behavior." The independent acceptance script `examples/sum-acceptance.mjs` is outside the project and explicitly loads the candidate under test through the **process cwd**, avoiding accidentally testing the original project.

```json
"verification": {
  "commands": [{
    "id": "sum-acceptance",
    "executable": "C:/Program Files/nodejs/node.exe",
    "args": ["C:/work/teamwork-dsh/examples/sum-acceptance.mjs"],
    "timeoutMs": 10000
  }]
}
```

Change the paths to the actual paths on this machine. Commands run in order in the acceptance copy; at least one is required, IDs must be unique, and executable must be an absolute path; use `shell: false` with no pipe or wildcard expansion. Windows wrappers such as npm.cmd are not valid direct executables; use node.exe and the corresponding JS entry. The acceptance environment only inherits PATH, system directories, temp directories, and language settings, and does not inherit API keys, TEAMWORK tokens, NODE_OPTIONS, etc.; there is no automatic dependency installation.

Each command's exit code, status, duration, and the last 16 KiB each of stdout/stderr are persisted as untrusted diagnostic output. Adding build artifacts is allowed, but rewriting/deleting the candidate's original inputs rejects the Gate and stops the remaining commands. The acceptance script should be controlled by the user and is best placed outside the implementer's working project; this version does not defend against malicious tests, cross-directory access by the same user, or escaped child processes.

## Bounded repair rounds (protocol 0.3)

Explicitly setting `"maxIterations": 2` in the Runtime's `verification` enables repair; the range is 1–5, includes the first round, and omitting it is equivalent to 1. This limit applies per requirement version; after an explicit user revision of requirements a new version's rounds begin, and model attempts across versions and derived tasks are separately limited by the shared budget below. This configuration is decided only by the operator; host/worker tools cannot change the limit. See the example in `examples/runtime.repair.example.json`. Each round launches an implementer and a fresh reviewer, which may increase model cost.

When the implementation reports incompleteness, the review rejects, or the acceptance command fails/times out, and integrity and evidence checks pass and budget remains, the Gate atomically persists the failed round and a new outbox intent in the same transaction, entering `repair_queued`. It then creates a fresh Attempt, dispatchKey, credentials, and working directory for the same WorkItem, increments epoch, and keeps the original objective/specRevision unchanged. The new working copy comes from the previous round's candidate, not from the original project, and does not carry acceptance-generated artifacts.

`iteration` in status indicates the current round; `history` retains the archived failed round's candidate digest, implementation report, review, acceptance output, and Gate reason. A repair worker receives at most 16,000 characters of untrusted diagnostic text; the new reviewer does not inherit repair feedback. New submissions from all old rounds are rejected, and historical idempotent receipt replays do not overwrite the new round.

Tampered candidate/review/acceptance inputs, acceptance-program spawn failure, stale or incomplete evidence, and unknown process exit do not auto-repair. Exhausting repair rounds ends in `rejected`; separately exhausting the shared model-attempt allowance enters `paused` with reason BUDGET_EXHAUSTED. Pending-dispatch repairs can be cancelled; on restart an unclaimed repair outbox can recover, while a claimed repair is still conservatively quarantined as `blocked`. The original project remains unchanged.

```powershell
$env:TEAMWORK_CONNECTION_FILE = 'C:\work\teamwork-runtime-data\connection.json'
```

### Structured requirements and change scope

`teamwork_start` and POST runs accept `spec`. See the full call example in `examples/start.scoped.example.json`, used with the sum acceptance example; it is a start request, not a Runtime configuration:

```json
{
  "commandId": "fix-sum-scoped-001",
  "objective": "Fix sum's empty-array behavior, keep other summation behavior, and do not install dependencies.",
  "spec": {
    "requirements": [
      { "id": "empty", "text": "sum([]) returns 0." },
      { "id": "addition", "text": "A non-empty numeric array still returns the sum." }
    ],
    "writeScope": { "files": ["sum.mjs"], "trees": [] }
  }
}
```

Requirement IDs are unique, at most 100; each text is 1–2,000 characters, total text at most 32,000. Structured requirements supplement the objective, not replace it. Unknown configuration fields are explicitly rejected; spec cannot modify the Runtime's acceptance program, increase the repair budget, or claim that external operations are already authorized.

writeScope's files are exact file paths, trees are directories and all their descendants, each at most 200; the lists are unioned. Paths are case-sensitive, use NFC Unicode and `/`, and reject absolute paths, `..`, Windows ADS/device, backslashes, and wildcards; `src` does not match `src-other`. trees's `"."` means the entire ordinary project; files/trees both empty means no final change is allowed. Adding necessary parent directories for authorized paths is allowed, but exact-file authorization does not allow deleting an existing parent directory or replacing it with a file; directory authorization also checks every actual child change. Case/Unicode aliases in a change are conservatively rejected.

A new Run without a spec saves `requirements: []` and the entire ordinary-project scope, preserving the old start call; when you need to narrow the scope you must explicitly provide a spec, and the host should not unilaterally widen the user-given scope. Old records without a spec in an existing database are read with the old semantics, without fabricating historical scope checks. Do not read a new-semantics data directory with an old Runtime.

spec is saved in `order.spec`, participates in the initial inputDigest, and is inherited across repair, pause/resume, and conflict-resolution work items. Only a user-authorized explicit revise can fully replace objective/spec; resolve.instructions, ordinary repair, and resume cannot widen the file scope. The acceptance program, rounds, and Attempt timeout are still managed by the operator's Runtime configuration, not a full unified RunSpec budget.

After confirming the implementer has stopped and fixed the copy, the Runtime compares the original baseline with the candidate, including additions/deletions, content, exec bits, and file/directory type changes; pause snapshots and the verification entry also check. `scopeCheck` records inputDigest, baselineDigest, candidateDigest, and violations, and only checks matching this Attempt's input and candidate can participate in the new Gate. Out-of-scope fails with `SCOPE_VIOLATION`, is not auto-retried, and is not marked submitted/verified/paused; the failed changes in the copy are retained, and the source project is not written back because of it. Integration prepare also independently checks the same candidate scope, and unrelated user changes do not count as candidate out-of-scope. A scope check cannot prove functional completeness and must still pass the other Gate conditions.

With structured requirements, the independent review's `report.review.requirements` must provide exactly one entry per ID, e.g. `{"id":"empty","verdict":"pass","evidence":"sum.mjs's empty-input branch returns 0 directly; the corresponding implementation was read."}`. evidence is 1–2,000 characters, describing specific observations and reasoning, and must not impersonate a Runtime command-execution result. A missing, duplicate, or unknown ID returns `REQUIREMENT_EVIDENCE_MISSING` with no auto-repair; a real fail returns `REQUIREMENT_REJECTED`, which can be repaired within the original round budget. Per-item reports are still model claims and must simultaneously satisfy the independent command, candidate integrity, and other review requirements; without verification enabled it is only report collection and does not claim requirements are verified.

These scope checks constrain acceptable output and explicit integration; they do not intercept every shell/OS write, nor detect temporary changes that were later restored. Working copies are not an OS sandbox; external file access, network/process permissions, and stronger isolation still require the operator and subsequent platform capabilities.

## Status meanings

Without verification, `queued → starting → running → submitted` is the report-collection chain; `submitted` only means a structured report was received, DSH reported a completed turn, and its dedicated runtime process exit is confirmed, with `gate` as `not_evaluated`.

With verification, the chain is `running → freezing → verification_queued → verification_starting → reviewing → validating → verified/rejected`. First close the implementer, then copy the Candidate and verify the SHA-256 tree digest; the fixed Candidate and verification outbox are atomically persisted before the review is dispatched. Both review and acceptance get independent copies from this Candidate. The review must submit `report.review.functionality`, `completeness` (pass/fail), and `findings`. Only when the implementation report has no unresolved items, both review items pass with no findings, all commands exit 0, and candidate/review input integrity is satisfied is the Gate passed. `verified` only means this candidate passed under that policy; it does not mean it was integrated, nor is it proof of absolute functional correctness.

`running/starting → stopping → cancelled` only completes after exit is confirmed. Unknown exit enters `blocked` and must not falsely report a successful cancellation. `idle` without submit, execution failure, or timeout enters `failed`. After the parent task's requirements are revised, stopped derived work enters `superseded` and the Gate is no longer valid; this is not a cancellation confirmation, repair completion, or integration success.

Result code stays in the status return's `order.workspace`; with verification, the accepted candidate is identified by `candidate.workspace` / `candidate.digest`. A snapshot is a logical content freeze, not an OS-immutable file; it is re-verified before the Gate, and subsequent use still requires checking the digest. Only a separately accepted automatic write-back policy or integration command can write the candidate back to the original project.

## HTTP interface (development protocol 0.3)

host and Runtime should be updated together; hello reports `verificationEnabled`, `maxIterations`, and `bounded-repair` / `pause` / `resume` / `revise` / `revision-context` / `candidate-recovery` capabilities. Old hosts on protocol 0.1/0.2 are rejected at handshake on version mismatch, avoiding silently starting a new workflow. Do not open a data directory containing new state with an old Runtime.

All requests use `Authorization: ****** JSON, 256 KiB limit. Only `127.0.0.1` is listened on; browser Origin and mismatched Host are rejected, and CORS is not enabled.

Connection failure returns the client `TRANSPORT_ERROR` with a filtered underlying error code, without outputting tokens. A network failure does not prove the command was not accepted by the service; the client does not auto-resend. Check status, or explicitly retry with the same commandId and original content; you cannot switch IDs to restart work. Cancel signals and timeouts retain their original exception semantics. In development regression, two first loopback request failures were observed; a single item, 300 Runtime start/stop cycles, and a simple same-port probe did not reproduce them, and the root cause is not yet confirmed; new diagnostics

## Artifact and change inspection

Each requirement version has its own baseline `baseline`, which includes uncommitted modifications in the ordinary project at capture time. Pause, repair, and resume within the same version do not replace the baseline; an explicit revise creates a new baseline, the old version is saved in specHistory, and the old baseline and artifacts are not deleted. Candidate and pause snapshots get an `artifactId` after being fixed; the registration record and related state are saved in the same SQLite transaction. New artifacts record specRevision and the available baselineId; paths in a model report are not the basis for artifact authorization.

`teamwork_inspect`'s `kind: "artifacts"` lists registered items; `manifest` requires artifactId; `file` requires artifactId and a normalized relative path; `changes` by default compares the current version's baseline with the current candidate, and can also specify a historical candidate, pause snapshot, or integration snapshot. Historical artifacts use the baseline of their own version and cannot apply a new version's baseline; when ownership cannot be confirmed from old registration and saved version/Attempt records, it is explicitly rejected without guessing. Baseline and context references themselves cannot be selected as candidates. The manifest describes added/deleted/modified/type_changed, including file digest, size, and exec bit; it does not mean the change has been integrated or accepted.

Manifest pagination uses `offset` and `limit` (default 100, max 500) and returns nextOffset; when continuing to read a change manifest, pass the returned candidate.id fixed, to avoid switching to a new round's candidate. File pagination uses byte offset and length (default 16 KiB, max 64 KiB), and a page is returned only after the full file digest verifies; normal UTF-8 pages return text, and binary pages or pages cut in the middle of a UTF-8 character return base64. nextOffset of null means the end.

All reads accept only references registered by this Run; worker credentials, cross-Run references, absolute paths, `..`, Windows ADS/device paths, symlinks, and digest mismatches are rejected. At most 2 file/manifest/change checks run concurrently, each with a 15-second limit. Artifact content is untrusted data. Records without a registered baseline/artifact in an old data directory are not guessed as readable files; the interface reports them missing.

File reads and change manifests do not write back to the original project, and there is no HTTP interface for arbitrary-path reads or arbitrary artifact registration.

### Integration conflict preview (read-only interface)

`teamwork_inspect` uses `kind: "integration"`, defaults to the current Candidate, and can also use artifactId to specify a registered historical candidate or pause/integration snapshot. The Runtime only reads its configured original project and does not accept a model-supplied target directory. The manifest compares the baseline of the selected snapshot's version, the selected snapshot, and the current project; user modifications unrelated to the candidate change are preserved, with no automatic same-file text merge. An old-version candidate always has candidateVerified=false and cannot be used for explicit integration of a new version.

Each disposition is `apply` (can be planned to apply), `already_applied` (target already has identical content), or `conflict`. Conflict reasons include `concurrent_change`, `ancestor_changed`, `descendant_changed`, `protected_path`, `path_alias`. The whole plan's status is clear/conflicts; even if the current page shows no conflict, conflictCount counts the full manifest. When deleting/replacing a directory, user-added or modified children block the operation; exclusion items inside the directory such as `.git`, `node_modules`, `.teamwork`, `.env`, `.env.*`, `.npmrc` also block the operation, and their contents are not read. Filter names are case-insensitive. Case or Unicode normalization aliases are conservatively reported as conflicts.

The preview is always `readOnly: true`, holds no lock, creates no persistent integration transaction, does not modify the Run, and does not mean the operator has authorized write-back. `candidateVerified` only means the current Gate-passed candidate is selected; it is independent of conflict status and cannot serve as final integration acceptance.

Pagination offset/limit is the same as the artifact manifest. The first screen returns a content-bound id; for continuation requests pass the same candidate.id as artifactId and the same id as planId. A change in ordinary-project content or the protected-path set returns `INTEGRATION_PLAN_STALE`, requiring re-checking from the first page. Concurrent edits can still occur during preview; it is not an atomic filesystem snapshot; a future executor must re-check every effect in a serial transaction and cannot directly execute an old preview. At most 2 concurrent checks and the 15-second request limit are shared with existing artifact reads.

### Enabling and initiating integration

Integration is not enabled by default. The operator adds `"integration": {"enabled": true}` to the Runtime config of a new data directory, and verification must be configured. See the full example in `examples/runtime.integration.example.json`. hello returns integrationEnabled; when enabled it reports integrate, integration-cancel, integration-keep-current, integration-resolve, resolution-context, automatic-integration. Enabling in config is not itself user authorization; it requires accepting the creation-time automatic policy or a single integration command; plugin load and status query are not authorization.

One authorization for automatic write-back: start provides `autonomy: {"integration":"on-gate-pass"}` and an explicit full spec (including writeScope), as in `examples/start.autonomous.example.json`. When the Gate passes, the automaticIntegration intent and the Gate event are saved in the same transaction; the Runtime waits for the active Attempt to exit, then generates the current three-way preflight and integration journal itself. It then automatically writes back serially, retains backups, and accepts the final merged tree, without the user or host sending integrate again. Without that field it is still manual mode and does not retroactively treat old tasks as automatic write-back. Independent acceptance and write-scope checks are not skipped because of the authorization method.

automaticIntegration.state's pending means waiting for dispatch or in read-only preparation; scheduled means an integrationId is associated (not that write-back succeeded); success still depends on integration.phase=succeeded. paused/cancelled means the intent was paused/cancelled by the user; failed means preparation failed and reason has an error code. A three-way conflict is recorded as integration.phase=conflict and does not overwrite the conflicting files; if conflicts=resolve was authorized upfront and there is a shared total budget, a resolution subtask is created automatically, otherwise the conflict remains pending. A source/Run preflight race rescans at most three times; if still unstable it records a failure and does not busy-loop indefinitely.

Before the intent creates an integration journal, ordinary pause/resume/cancel on the verified Run can control automatic write-back; Run.phase remains verified, and the pause state is in automaticIntegration.state; pausing does not revoke the passed candidate verification. Once there is an active integration journal, use that integrationId's cancel interface. Restart continues an authorized pending intent and reuses already durably committed journals/receipts; a manual integration of the same current candidate initiated first is also reused and not written back twice. An accounting exception after the journal is committed stops scheduling and retains the pending-recovery state, and is not misreported as "write not accepted."

revise does not inherit the old automatic write-back authorization; only when the revision request provides autonomy again is the new target/scope's automatic write-back authorized. Pending/paused intents of the old version and stopped descendants are cancelled in the same revision transaction. Ordinary repair/resume does not widen the scope and keeps the original authorization. An explicit conflict-resolution subtask inherits the parent task's existing automatic write-back policy, and enabling conflicts=resolve also automatically creates that subtask.

After the user authorizes write-back, first call `teamwork_inspect` (kind integration) to get planId, i.e. the id returned by the preview; then call `teamwork_integrate`, e.g. `{"runId":"...","commandId":"integrate-001","type":"integrate","expectedRevision":42,"planId":"<64-char digest>"}`. expectedRevision is the latest **Run revision**, not the preview plan ID or integration revision. The HTTP equivalent is POST integrations, omitting runId in the body. The model cannot supply a target directory, modify acceptance commands, or skip the Gate. Repeated/concurrent requests with the same commandId and identical content get a durable receipt; the receipt is the state at acceptance, not the latest execution state.

The Runtime integrates serially after the current model Attempt drains, and does not dispatch new working copies during that time. GET Run's `integration` shows the latest integration; `teamwork_inspect` (kind integrations) queries history with pagination. Each integration update is committed with the Run projection and SSE events in the same SQLite transaction. **Run.phase remains verified; only integration.phase of succeeded means that final merged tree passed acceptance.** prepared/applying/snapshotting/validating during integration are not success, and neither are conflict/failed/blocked/abandoned.

To stop an integration use `teamwork_integrate`'s type cancel, providing integrationId and the latest **Integration revision**. An unclaimed prepared can be cancelled without modifying the project; an already running one first records cancelRequested and waits for the executor/direct-acceptance process to stop, which may leave partial writes, then enters blocked. Ordinary teamwork_control cancel does not treat a verified Run still integrating as cancelled. A failed or blocked integration retains the source-directory lease, pauses new work dispatch, and waits for handling.

### Integration journal and final acceptance

Internal prepare requires the current Run to be verified, the Gate passed, input identity consistent with the candidate registration, and provides the current revision and preview planId. The same SQLite database stores `integration_jobs`, `integration_events`, and `integration_leases`; the source-directory lease blocks a second unresolved integration. An exclusive reservation file is also created in the project parent directory to prevent executors of different data directories from operating on the same project at the same time; unknown owners are not guessed by PID or preempted. A recovering caller must still first hold exclusive ownership of the Runtime data directory.

The executor creates a unique `.teamwork-integration-<id>` directory at the source directory's level to hold owner, original-file backups, snapshots, and the acceptance copy. Each effect first persists intent, then operates on the file, and finally persists done. Old files are preserved to backup via same-volume rename; new files are first copied and verified to staging, then published atomically via an exclusive hardlink, and the staging link is removed after completion, so a normally completed target does not share an inode with staging. rename is not used to overwrite the target, and on a cross-device error it does not fall back to "copy then delete." Directory deletion uses only non-recursive rmdir, and new user files appearing in a directory block the deletion.

After process exit, the Runtime continues an authorized pending-dispatch integration, and reconciles unconfirmed file effects by backup digest, staging digest, and publication identity; cases that cannot be proven enter blocked. Old internal experiment records not marked host-authorized are not auto-dispatched. If a new user file appears at the target after the original file was moved, the new file is not overwritten and the backup is not forcibly restored. Partial writes already made, backup directories, and reservation are all retained; failure is not a promise that "the original project is unchanged." No automatic rollback is provided.

After writing completes, the target ordinary file tree must equal "the user project at prepare time + the candidate change," including the user's original unrelated modifications. The final merged tree is independently frozen, then copied to another directory to run the original acceptance commands; build output is not written into the project/frozen snapshot, and the original inputs cannot be rewritten by acceptance. Final success also requires the current project to still match the merged tree, the snapshot digest unchanged, and every command to have a current result with exitCode 0. When the candidate Gate passes but the final integration acceptance fails, it is internally recorded as failed, and writes and backups are retained, without impersonating integration success.

The final snapshot is registered as an integrated artifact before acceptance and can be inspected through the existing manifest/file interfaces; the artifact's existence itself does not mean acceptance passed. The acceptance command intent is saved before the process is launched; if there is no durable result or stop evidence, recovery enters `EXTERNAL_STATE_UNKNOWN` and does not auto-rerun a command that may have external side effects. A normal cancellation persists commandStop after getting direct process-exit confirmation and does not treat it as passing command evidence. Tests cover a real child process exiting between file move/publish and journal acknowledgment, exiting before the final command result is saved, SQLite reopen, and user changes and path redirection on recovery.

### Manually choosing to keep current files

When the user explicitly chooses to abandon this integration and keep the current project, they can call `teamwork_integrate` on a stopped failed/blocked integration, type abandon, with integrationId, the latest Integration revision, the current integration preview's targetDigest, and a non-empty reason. This operation does not retry, roll back, delete backups, or mean the task succeeded. It only releases **that integration's own** reservation and source lease when the current project digest still matches, moving state from abandoning to abandoned, allowing subsequent explicit work.

A commandIntent with unknown exit cannot be cleared by abandon; a textual explanation cannot replace exit evidence; a still-running writer cannot be abandoned either. A foreign reservation is not preempted or deleted. The decision and command receipt are persisted first; if the process exits after releasing the reservation, recovery completes without rewriting the project again. If the user modifies the project in the meantime, it reports stale and retains the occupancy, requiring a re-check before submitting a new decision. The recovery directory is in recoveryDirectory; backups are still retained for manual inspection. Strong-evidence reconciliation of unknown processes and restore/revert options are still to be developed.

These guarantees target cooperative local tasks and process crashes, and are not an atomic transaction of the whole tree, a power-loss durability guarantee, or a sandbox against malicious filesystem races by the same OS user. Windows permissions rely on inherited ACLs. Original-file backups are not auto-deleted; a separate retention/cleanup policy is needed later.

### Creating conflict-resolution work items

Pre-authorized automatic path: start/revise autonomy provides `{"integration":"on-gate-pass","conflicts":"resolve"}` and requires a configured finite shared model-attempt budget. Budget must be provided at creation; on revision the existing root budget is reused and a revision cannot create a new allowance. See the example in `examples/start.autonomous.example.json`. Omitting conflicts retains manual conflict handling and does not widen the old authorization.

After preflight finds a conflict, the Runtime automatically prepares three-way references in the original target/write scope and creates a new Run, without the model requesting approval step by step. The subtask inherits the automatic policy and budget, still goes through independent review, acceptance, and Gate; further conflicts can produce descendants, all drawing from the same root allowance. The fixed automatic resolution instruction is not repeatedly appended to inherited requirements. When budget is exhausted, only one pending-recovery subtask is created and dispatch is paused, without repeatedly spawning new model processes; a failed Gate is still bounded by the configured repair rounds and does not bypass rejection. If the conflict has already disappeared, preflight and integration are automatically redone without starting an extra model.

The child Run, outbox, the root automatic intent's resolutionRunId, and the request receipt are committed in the same transaction. Restart can continue creating a subtask from a committed conflict, and can also recover an existing pending-dispatch subtask, without duplicate dispatch; on a race with manual resolve, the same subtask committed first is reused. Pause/cancel can revoke an automatic intent not yet committed; after prepare completes, the authorization is also checked in the commit transaction.

After the automatic task is derived, the parent Run retains the historical conflict state, and `automaticIntegration.resolutionRunId` points to the child Run that actually continues execution. Using `scope: "workflow"` below, you can track and control the whole chain directly on the root task, without approving or controlling subtasks one by one. Compatible single-Run pause/resume/cancel still returns DERIVED_CONTROL_REQUIRED and gives the child Run ID, preventing a single-Run operation from being mistaken for a recursive stop. Identical retries of historical control commands still return the original receipt and are not affected by subsequent derivation.

### Status and control of the whole task chain

`teamwork_status({"runId":"<root>","scope":"workflow"})` returns the status of the root task and all registered descendants, integration records, deduplicated shared budget, active Runs, and effective leaf nodes. A parent task's historical conflict does not mask the final integration already completed by a resolution subtask. `state: integrated` requires the effective leaf node's final merged tree to pass acceptance; `verified` only means candidate acceptance completed, and the two are not mixed. Unknown processes or unhandled failed writes are reported as blocked first.

Control example (the version must come from the just-queried workflow.revision):

```json
{
  "runId": "<root>",
  "scope": "workflow",
  "commandId": "pause-entire-workflow-001",
  "expectedWorkflowRevision": "<64-char aggregate revision digest>",
  "type": "pause",
  "mode": "drain"
}
```

The HTTP equivalents are GET `/v1/runs/{id}/workflow`, POST `/v1/runs/{id}/workflow/commands`; the POST body does not contain runId/scope. The interface only allows host credentials. The aggregate query uses the same SQLite read snapshot, and the version covers all members, integration journals, shared budgets, and parent/child control records; any change rejects stale operations. Pause/cancel intents, all related Run/outbox/integration cancellations, control records, events, and the unique command receipt are committed in one transaction. HTTP 202 only proves the command was accepted, not exit; re-query the actual state.

- `pause` defaults to drain: blocks new dispatch, new derived tasks, and not-yet-started write-back, waits for running tasks and claimed writes to finish; state is first pausing, and only after confirmation is it paused. interrupt requests interruption of the owned running process.
- `resume`: waits for the whole group of related processes to be confirmed stopped; preserves the subtree's independent pause/cancel records, does not bypass a parent hold, does not reset the shared budget, and does not re-approve ordinary steps. If the consumed budget is insufficient, the whole resume transaction rolls back. Continuing implementation uses a new Attempt, not reconnecting to the old process.
- `cancel`: cancels all registered descendants, pending-dispatch automatic intents, and cancellable integrations, and permanently closes that subtree's dispatch authorization. Cancel cannot be changed to pause-then-resume; new complete work requires a new root task. Cancel does not guarantee file rollback.

An integration already written that is interrupted/cancelled may retain partial files, backups, and the source lease, with state blocked, and cannot masquerade as a safely resumable pause. An existing explicit "keep current files" decision can complete cleanup and release its owned lease under a hold, but this does not equal final acceptance success, nor does it imply restarting model work. Unknown processes cannot skip exit verification with this decision.

You can point runId at a subtask to control only its descendants, without affecting sibling tasks or other root tasks. The current Runtime processes source integrations serially; a paused prepared integration retains the source lease and therefore also blocks new task dispatch until the integration is resumed or cancelled; it does not interrupt unrelated running processes because of this. All control is the user's ability to intervene at any time, not an approval point that must be called for every autonomous step. Multi-day continuous operation and full planning still require subsequent verification.

This automatic path only handles three-way preflight conflicts that have not been written. failed/blocked integrations must still prove the old writer/command has stopped, and cannot automatically abandon, restore backups, or clear unknown processes. Full long-term autonomous operation also needs evidence reconciliation and subsequent policies for these exceptions.

After the user authorizes conflict resolution, call `teamwork_integrate` on the recorded `conflict` integration, type resolve. First refresh `teamwork_inspect` (kind integration) to get the current planId, and query the integration's latest revision. Example:

```json
{
  "runId": "<parent Run ID>",
  "integrationId": "<conflict integration ID>",
  "commandId": "resolve-001",
  "type": "resolve",
  "expectedRevision": 1,
  "planId": "<64-char digest of the current preview>",
  "instructions": "Keep the user-added edge handling while merging in the original candidate's functionality; do not install dependencies."
}
```

expectedRevision is the actually queried **Integration revision**; the example value must not be copied verbatim. The HTTP equivalent is POST integration commands, omitting runId in the body. failed/blocked integrations must first satisfy the exit-evidence requirement, and the user must explicitly complete the abandon/keep-current-files decision to reach abandoned before resolve. At that point, even without a file-level conflict, semantic problems such as final-acceptance failure can be handled. An unresolved source lease, active integration, or unknown commandIntent cannot be bypassed by creating a work item. If the current conflict corresponding to the old conflict has disappeared, resolve returns CONFLICTS_CLEARED, and you should re-check and separately authorize integration.

The new work item inherits the original objective and the operator's acceptance policy, creates a fresh Run/WorkItem/Attempt, increments specRevision, and starts epoch at 1. It starts from the **current user project** frozen at resolve time, not from the old proposal, and does not directly modify the original project. This current copy becomes the new Run baseline; the old base/proposal serve as registered read-only context references. The new Run, three-way artifact registration, outbox, parent-integration association, events, and command receipt are committed in the same SQLite transaction and roll back together on failure. A failure during preparation may retain an unregistered copy, but it is not dispatched or written back to the project.

The implementer and fresh read-only reviewer additionally get `teamwork_context`: `kind: conflicts` paginates conflicts; `kind: manifest` requires `version: base / proposal / current`; `kind: file` additionally requires a normalized relative path. Pagination parameters are the same as the artifact interface; arbitrary artifactId, external directories, or cross-work-item credentials are not accepted. An ordinary worker does not load this tool; active credentials only allow reading their own registered context, and old readers are rejected after submit, cancel, interrupt, or epoch replacement. Registered digests are verified when reading files, and all three-way inputs are checked before dispatch and before the new Gate. The copy is still a logical freeze, not an OS-immutable file.

The resolver must preserve user changes and consider non-conflicting functionality in the old proposal, not just process the conflict list and discard the rest of the objective. The new review independently checks the original objective, three-way references, and additional requirements, and the new acceptance reruns; the old review and old command results are not used as new Gate evidence. Prior integration diagnostics are at most 16,000 characters and are only untrusted hints. Each instructions is 1–16,000 characters; multi-generation resolution work items inherit all additional requirements, joined by newlines up to 32,000 characters, and exceeding the limit explicitly returns RESOLUTION_BUDGET without silent truncation.

The new Run supports bounded repair, pause, and resume; after queuing, a restart still uses the frozen current and does not absorb later source-project changes. When the same integration already has an active, paused, verified, or blocked resolution work item, duplicate creation is rejected; only after the previous one failed/cancelled/rejected can a replacement be explicitly created. resolve starts new model work and may incur cost; it does not loop automatically.

After the new candidate passes the Gate, if it inherited an accepted automatic write-back policy it auto-preflights/integrates; otherwise re-preview for the **new Run** and explicitly initiate integrate. The final merged tree must pass acceptance again for that integration to count as successful. If the user modifies the same files again in the meantime, a new conflict arises; with conflicts=resolve enabled, descendant repairs are automatically continued within the shared budget, otherwise an explicit work item is still required. This is not an unconditional overwrite or backup-restore feature.

## Recovery and boundaries

### Shared model-attempt budget

The final goal is one authorization followed by days of autonomous operation, not approval of every step. The current model-attempt budget is an optional total runtime allowance: creating a Run can provide `budget: {"maxModelAttempts": 200}`, an integer in 0–1000; implementation, review, repair, and derived work within the allowance need no per-occurrence additional approval. 0 is used to create but not start the model, and omitting it preserves the old behavior (no cross-round total allowance). This count does not replace the per-requirement-version maxIterations, nor does it meter tokens, request counts, or tool calls within a session. Long-term autonomous planning, unified workflow control, wall-clock deadlines, and long-duration recovery are not yet complete, and multi-day unattended operation cannot be claimed on this basis.

Before each executor.create, the Runtime transactionally writes model_reservations, the shared count, and events. Implementation/review, new resume Attempts, repair, requirement revision, and conflict-resolution descendants all use the same budget.rootRunId. Sibling tasks cannot each obtain the remaining allowance. Startup failure, cancellation, or unknown exit after reservation still retains the count, without guessing whether cost was incurred, auto-refunding, or redispatching the same Attempt.

When the allowance is insufficient, the executor is not started, the work/candidate is retained, and it enters paused with reason BUDGET_EXHAUSTED. This is an exceptional decision beyond the initial resource authorization. After the user adds more, call teamwork_control on the root Run:

```json
{
  "runId": "<budget.rootRunId>",
  "commandId": "allocate-002",
  "type": "budget",
  "expectedRevision": 42,
  "expectedBudgetRevision": 200,
  "maxModelAttempts": 300,
  "reason": "User approved increasing the total attempt allowance for the run"
}
```

Both revisions must use the latest queried values. maxModelAttempts is the new total limit, not an increment, and must be greater than the old limit; budget.revision increments independently with shared reservation and top-up. The top-up reason is saved in the durable receipt and budget.lastIncrease, and the same commandId/content replays the original receipt. Subtasks can only top up through the budget root Run; worker credentials have no allocation permission. Allocation does not implicitly resume user-paused tasks; afterward you can explicitly resume the paused Runs that need to continue. Unknown processes remain blocked, and increasing the budget does not release quarantine. status.budget always reads the shared ledger; a historical command receipt is a snapshot at acceptance.

hello reports model-attempt-budget / budget-increase, and the actual metering boundary of modelAttemptBudget. Token/amount budgets, cross-Run wall-clock deadlines, and operator-level hard resource ceilings are still to be implemented. Insufficient allowance does not automatically switch models or paid providers. File integration and its acceptance commands do not consume model-attempt slots, nor do they thereby gain new write-back authorization.

### Explicit requirement revision

When the user changes the objective or authorized scope, submit a full new objective/spec and reason via `teamwork_control`'s `type: "revise"`. It is not a partial-field patch, does not inherit omitted new requirements, and is not an entry for ordinary repair or increasing the retry allowance. The revision in the example must be replaced with the latest Run revision:

```json
{
  "runId": "<Run ID>",
  "commandId": "revise-001",
  "type": "revise",
  "expectedRevision": 12,
  "objective": "Add new empty-input handling while keeping the existing numeric summation behavior.",
  "spec": {
    "requirements": [{ "id": "empty", "text": "Empty input returns 0." }],
    "writeScope": { "files": ["sum.mjs"], "trees": [] }
  },
  "reason": "The user replaced the objective and narrowed the allowed file modification scope."
}
```

HTTP uses POST Run commands, omitting runId in the body. It must be in an undispatched, fully paused, or stopped submitted/verified/rejected/failed/cancelled state; running, stopping, or blocked do not accept revision. Explicitly pause/stop first and confirm exit. If there are descendants not yet stopped or with unknown exit, it returns REVISION_ACTIVE_DESCENDANTS; it is also rejected when there is an integration writer, pending, or retained source lease. After integration.phase=succeeded, if there is still brief reservation cleanup, it may return INTEGRATION_BUSY; wait for it to actually finish and retry with the same command content. A revision mismatch requires refreshing state first; identical objective/spec returns SPEC_UNCHANGED, and you cannot rerun by only modifying reason.

Revision retains the Run and WorkItem IDs, creates a fresh Attempt, dispatchKey, credentials, and directory, increments specRevision and epoch, and resets the Gate to not_evaluated; the new version's iteration starts from 1. The current report/candidate/review/validation/scopeCheck/integration projections are not carried over. The old version's complete state and rounds, pause evidence, and artifact references are saved in specHistory; historical integrations are still queryable through integrations. The new baseline comes from the current project frozen at revision time, not from the old candidate, and the project is not written back. Old results already integrated therefore belong to the new baseline and can correctly express subsequent modification or removal under the new requirements.

Currently invalidation is by the entire derived branch, without pretending there is fine-grained dependency analysis. The derivation relationship is preserved via parentRunId; stopped/queued descendants become superseded in the same transaction, the gate is no longer valid, the outbox is no longer dispatched, and supersededBy marks the triggering Run and new version. Running or unknown descendants are not forcibly cleared by a text revision. The old Gate and old integration are not allowed to create resolution work items or perform write-back for the new version. The new version, old-evidence archiving, new-baseline registration, descendant invalidation, events, outbox, and idempotent receipt are committed together or rolled back together.

The revision implementer and fresh reviewer read the current version's registered references via teamwork_context: current is the new baseline, base is the available old baseline, and proposal is the available old candidate or pause snapshot. Old versions that are missing or already damaged are listed in revisionContext.unavailable, and the corresponding read returns CONTEXT_VERSION_MISSING without fabricating content; when conflicts returns available=false you cannot infer there is no conflict. Database and program errors are not downgraded to missing references; the revision fails and no receipt is committed. Old references only provide implementation clues and do not inherit the old objective or widen the new scope. Reference tampering after binding blocks the new Gate. Fully replacing a task does not require bringing all changes of the old candidate into the new version.

The new version needs fresh submission, per-requirement review, and command acceptance. When the revision request explicitly renews autonomy, it auto-preflights/integrates after passing; when omitted, the old authorization is not inherited and explicit integration is used instead. A queued revision still uses the frozen current across a SQLite restart and does not re-capture later source modifications. Revision consumes new model work and may incur cost; cross-version total token/time/cost budgets, plan revision, and finer impact analysis are still to be implemented.

### Pause and manual resume

Pause example: `{"commandId":"pause-001","expectedRevision":12,"type":"pause","mode":"drain"}`. Resume example: `{"commandId":"resume-001","expectedRevision":15,"type":"resume"}`. Tool calls also need `runId`; the HTTP route already contains runId. revision uses the actual value returned by each query; an exact retry must reuse the same commandId and content.

`drain` (default) waits for the current model Attempt or current acceptance command to finish and does not dispatch the next item. `interrupt` requests stop and confirmation of owned execution exit. Both first show `pausing` (`pause.stage` retains the active stage), and only after the resumable content is frozen do they show `paused`. A queue not yet dispatched goes directly to paused. You can cancel during pause; drain can be upgraded to interrupt, but cannot be downgraded in reverse.

Only paused can resume. After interrupting the implementer, a fresh Attempt, credentials, and directory are created from the pause snapshot and checkpoint, epoch is incremented, and iteration is not increased; the original requirements and repair budget are unchanged. Previous records are saved in `suspensions`. If the copy has not fully completed, the partial copy is not used; a complete input is remade on resume. The report is only a hint context, and the implementer after resume must submit again.

If the implementer already finished normally and the candidate is fixed, verification is resumed directly without rerunning implementation. Resume after pausing review/acceptance creates a fresh review and acceptance copy and reruns verification; the old verification record is kept in suspensions and not used for the new Gate. Therefore resume may call the model again and re-execute the acceptance program; these programs should be rerunnable. A normally drained submission without verification enabled can resume directly as submitted without starting a new model.

Unknown exit is still blocked; a natural execution failure is not wrapped by pause into a success or resumable result. When the pause snapshot/candidate is tampered with, resume fails before starting a new process.

### Restart and isolation limits

- Unclaimed outboxes of queued, repair_queued, and verification_queued can be dispatched on restart; verification_queued starts verification from the fixed Candidate, re-verifies the digest, and does not rerun implementation. paused stays paused across restart and only continues on explicit resume. claimed, freezing, reviewing, validating, pausing interrupted still conservatively enter blocked; unknown old processes are not reused. The review dispatch intent is persisted before the process is created, and completed command evidence is not lost; unknown exit stops this Runtime's new dispatch.
- An abnormal exit leaving `runtime.lock` rejects startup. First manually confirm the old Runtime and its workers have stopped, then archive that lock file; keep SQLite and the attempt directories, then restart. Processes are not killed based only on PID.
- The initial copy includes uncommitted changes of ordinary files, excluding `.git`, `node_modules`, `.teamwork`, `.env*`, and `.npmrc`; symlinks/junctions/special files and existing targets are rejected, limited to 20,000 entries / 100 MiB. Subsequent copies of Candidate/review/acceptance no longer filter files, to avoid silently changing the candidate. It is not a full dependency image, and no dependency-installation flow is provided.
- Copies are not an OS sandbox, and copying is not an atomic snapshot of the original directory. DSH's own sandbox/approval policy still applies; only when hard isolation is explicitly configured is there a corresponding security guarantee.
- The implementer guard limits known read/write/search/shell/report tools and PTC transport, and rejects other tools and `run_in_background`. The reviewer is forced to present with native tools, only allows read/search/report, and forbids shell, write, and code execution. shell and acceptance commands can still produce external processes; this version only confirms owned direct processes and does not guarantee recovery of escaped child processes.
- `connection.json` is a host management credential; do not commit it to the repository or provide it to the model. Directory access permission on Windows relies on ACLs, and Unix mode cannot replace Windows ACLs. This implementation does not defend against malicious processes under the same OS user reading files or the environment.
- Explicit integration, final acceptance, file-effect recovery, keep-current-files handling, and new conflict-resolution work items are wired into Runtime/DSH; strong-evidence reconciliation of unknown processes, full RunSpec, and the complete first-version release gate are not yet complete.

## Source boundaries

`contracts.ts` / `kernel.ts` do not import DSH. `store.ts` / `runtime.ts` are reusable execution services; `client.ts` is a host-agnostic HTTP client. DSH dependencies are concentrated in `driver-dsh.ts` and `plugin-dsh/`, preserving replacement points for subsequent OpenCode and Pi entries and executors.

Interfaces are governed by the actual types and tests of the pinned npm versions, and do not float with GitHub master.
